# 立项引导（Kickoff）

适用：项目没有 docs/PROJECT.md，用户描述了一个想法。目标是在最少的来回内产出可确认的立项草案，而不是无止境提问。

## 访谈协议

- 每次最多问 **2 个最影响方向的问题**，并同时给出合理默认值及其影响。
- 把信息分三类：必须明确 / 可以默认（标"暂定假设"）/ 以后再决定。可以默认的不要问。
- 用户说"不懂技术，你来推荐"时：给一套主推荐，标出假设，直接起草 Brief；只问一个当前必须确认的关键问题。

问题清单（按方向影响排序，覆盖即止，不必全问）：

1. 谁会使用？最常做的一个动作是什么？
2. 需要登录或多人使用吗？在哪些设备上用？
3. 什么时候想开始用？有预算或已有工具的限制吗？

影响人身安全的产品（健康、医疗、金融建议），先明确风险边界，不把一般建议说成专业判断。

## 暂定假设台账

每个默认值记入 PROJECT.md 的"暂定假设"表：假设 / 若错了的影响 / 如何验证。
立项阶段用口头确认验证；进入实现后用 Spike 或真实使用验证。
AI 主动补充但用户没有提出的 MVP 项（例如备份、导出、同步）必须标成“建议项”或“暂定假设”，说明加入原因并等待范围确认；不能悄悄把建议升级为已确定的必做项。

## Project Brief 模板

```text
项目名称：
目标用户：
核心问题：
核心价值：
MVP 必做：
明确不做：
成功标准及衡量方式：
平台、时间、费用、数据等约束：
主要风险与待确认假设：
下一阶段及进入条件：
```

成功标准必须可判断："能导入账单"不够，要写清支持的输入、成功结果、失败反馈。

## 反方评审

草案完成后自己先过一遍再交用户：需求有没有互相矛盾？价值是否撑得起做这件事？范围是否过大？主要风险是否已列出？修订后再请用户确认。

## 技术栈推荐规则

技术栈服务于已确认的用户流程与约束：

- 只给一套主方案，说明它解决什么问题、对使用/费用/维护/部署的影响、已知限制。除非差异会改变用户选择，否则不给选项清单。
- 成熟现成工具优先于自建基础设施。
- 典型判断：单人本机记录 → 本地优先的响应式网页 + 简单存储；多人跨设备同步 → 才需要账户、服务端、部署方案。
- 关键未知能力先走 Spike（见 references/planning.md），确认后把方向和理由写入架构基线或关键决定表。

## 立项完成的判定

Brief、MVP、明确不做项、首批验收标准、一套主技术方案全部就绪。

第一条回复必须包含：当前处于立项阶段、依据的暂定假设、最多两个高影响问题（或信息已足够时一份可直接确认的草案）、唯一下一步。
只给产品建议、一次列很多问题、或以"我建议接下来……"结束，都算未进入领航模式。

确认后创建 docs/PROJECT.md，进入产品设计（用户流程 → 每功能验收标准），再进入架构。
