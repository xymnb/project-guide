# Coding 循环细节

## 按变化选验证

| 变化 | 首选证据 |
|---|---|
| 领域规则 | 对应规则测试 |
| API 契约 | 接口及集成验证，客户端一致性 |
| 前端组件 | 相关类型、组件行为检查 |
| 数据库结构 | 迁移及数据兼容验证 |
| 完整纵向功能 | 跨层集成验证 |
| 核心用户路径 | 浏览器实际操作 |
| 里程碑或发布 | 预定的整体验收集合 |

验证命令必须来自当前仓库实际配置（查 package.json、pyproject 等），不套用别的项目的命令。
按变更风险选验证范围：文字调整、业务规则修改、数据库迁移需要的证据不同——少做无用测试，但该有的一样不少。

## 默认工作顺序

检查现有文件与工作区修改 → 理解任务 → 原地完成最小变更 → 验证受影响行为 → 检查差异 → 报告。

禁止：为改一个功能复制整个项目、保存旧实现副本、另建平行测试工程、顺便重构无关模块。
新文件必须有明确职责；测试尽量用现有设施。

## 问题定位循环

卡住、测试反复失败、行为与预期不符时，先缩小问题再改代码：

1. **稳定复现**：一条命令或最短操作能重复触发。
2. **收集事实**：完整错误、复现命令、环境与版本、相关输入输出、当前 diff。
3. **可检验假设**：每条假设配一个能推翻它的检查。
4. **区分性检查**：先执行最能区分不同假设的那一项。
5. **单变量修改**：每次只改一个主要变量。
6. **复验**：修复后重跑原复现 + 受影响验证。

禁止制造通过：跳过测试、吞异常、放宽断言、修改预期结果。
同一思路无新证据反复失败，或修改开始越过 Task Packet 范围 → 停止重试，报告事实、失败尝试和需要的决定。

## 范围刹停清单

出现以下信号立即停下、报告影响、转入决策：

- 需要新增一级业务域
- 更换数据库或运行时
- 改变核心契约（API 语义、数据所有权）
- 突破迁移授权
- 跨范围大重构

普通实现困难不自动等于架构变更。

## 完成报告至少包含

改了什么 / 验收证据（命令 + 结果）/ 没有做的检查 / 剩余阻塞。
"代码写完"不代表交付完成。

## Git 纪律

- Git 只保存已提交快照；未提交修改、数据库内容、外部配置不靠 Git 恢复。
- 小型个人项目：主分支上按一个边界清晰的任务一次提交即可；需要并行开发、评审或发布维护时再上功能分支，并说明理由。
- 功能验收通过、高影响迁移前、形成发布候选时：检查 status 和 diff、运行相应验证、只暂存当前任务的文件后提交。
- 提交信息说明"为什么改、行为如何变化"；提交 ID 或标签记入状态文件。
- 密钥、数据库备份、无必要的生成物不进代码历史。
