# 验收与发布

## 验收流程

冻结可识别的候选版本 → 自动检查 → 用户场景 → 收集证据 → 反馈分类 → 有界修复 → 回归 → 最终判定。

判定只有三种：

- **ACCEPTED**：规定条件均有证据支持 → 进入下一个门。
- **REJECTED**：有具体条件失败 → 修复失败项后复验。
- **BLOCKED**：外部依赖或未决决策卡住验收 → 解决指定阻塞。

## 反馈分类（验收时冒出的新想法）

| 类型 | 走向 |
|---|---|
| 功能缺陷 / 验收相关 UX 问题 | 受限 Repair Task（只许相关改动） |
| 新需求 | Change Request，评估后决定归属 |
| 偏好、锦上添花 | Post-MVP Backlog |

不能把新增范围包装成本版本验收失败。修复后的新候选版本须重新验证受影响场景。

## 测试证据是否可信

测试通过只说明它检验的内容成立，先确认它检验的是已批准的需求而非实现者自己的猜测。审查关键测试时核对：

| 检查 | 要看到的证据 |
|---|---|
| 预期独立 | 预期来自验收标准、已确认样例或独立数据，不是复制当前实现 |
| 断言命中行为 | 检查业务结果、状态变化或用户可见结果，不只检查"调用成功" |
| 失败路径真实 | Mock 和 fixture 能真正触发要验证的失败或边界情形 |
| 回归有效 | 修复前能复现失败，修复后原复现 + 回归检查通过 |

本地单元测试、浏览器验收、人工确认、真实部署冒烟分别记录。AI 不能代替用户声明人工验收已通过。

## 面向用户的验收引导

自动检查完成后，先核对候选版本身份、实际测试/构建入口、运行前提和用户可打开的入口。检查仓库中的真实脚本与本轮命令结果；只会输出“pass”的占位脚本、状态文件里的历史结论或用户转述都不能算本轮验证证据。

入口缺失、无法启动或候选版本无法对应时，判为 **BLOCKED**。AI 的下一步是先定位或准备入口；仍需用户信息时，只索取一个最小信息。不要让非技术用户自行“打开候选版本”或猜运行命令。

即使当前唯一下一步只是解除入口阻塞，也要用一句话交代后续门的顺序：入口可用 → 给出可照做的人工场景并记录结果 → 用户明确确认 → 取得具体部署授权 → 真实部署冒烟 → 最终发布判定。这样既保持一步一做，也不让用户误以为提供入口后就会直接上线。

确认入口可用后，把人工验收写成用户可照做的指引，每个场景包含四件套：

1. 打开哪里 / 运行哪个已准备好的入口。
2. 依次做哪些操作。
3. 每一步应看到什么结果。
4. 不符合时反馈什么（截图、报错文字、复现步骤）。

无需用户操作时明说"当前无需你操作，我将继续 <下一步>"。
问题聚焦可判断的结果（如"这个导入预览能否让你知道哪一行出错"），不要求用户判断代码质量。

汇报测试或构建结果时标明证据来源：**本轮已运行**、**状态记录称**或**用户称**。后两者未经复验不得表述为“已通过”。

## 发布判定

候选版本发布前逐项核对：

- 所有发布阻塞问题已关闭。
- 核心用户场景通过。
- 架构边界保持一致。
- 迁移与恢复方案已验证到规定程度。
- 真实部署健康检查 + 生产冒烟通过（最短用户路径）。
- 人工验收结论有实际确认。
- Release Baseline 可对应：代码版本（提交/标签）、架构基线版本、已应用迁移、配置与运行时、验证与恢复方案。

缺失证据不能当作通过。发布后：剩余非阻塞项进入同一 Post-MVP Backlog，观察真实错误率、成本、卡顿；线上缺陷走有界 Hotfix，普通新需求走变更流程。

## AI 功能评估（仅当产品实际使用模型 / Agent / 生成式输出）

要回答的不是"这次回答好不好"，而是"真实、边界、失败输入下是否持续满足产品目标"：

- 用户任务、不可接受的输出或工具动作、成功标准。
- 固定样例集：常见 / 边界 / 对抗 / 历史失败，脱敏后可重复运行。
- 自动检查（结构、事实引用、工具参数、预算、阈值）+ 人工抽样复核，两者分歧时如何修订。
- 版本信息：模型、提示词、工具契约、检索或数据快照、评估代码。
- 更换模型/提示词/工具/关键规则时，对比同一批样例；线上代表性失败经脱敏审核后补入样例集。

模型输出不稳定，一次演示成功不等于质量受控。普通确定性功能不走这套，按常规测试与验收即可。
