# 操作权限与授权边界

任务范围说明"改什么"；操作权限说明"可以在哪个环境做哪些动作"。两者一起写进 Task Packet，才能既不反复停在普通工作上，也不把本地权限误解成可以改变外部系统。

## 四类操作

| 操作 | 授权来源 | 执行前核对 |
|---|---|---|
| 读代码、配置样例、测试、本地日志 | 当前任务的理解需要 | 只读相关位置；不把密钥或私人数据复制进报告 |
| 本地修改代码、文档、测试 | Task Packet 允许范围 | 保留现有修改；验证受影响行为 |
| 安装依赖、改锁文件、运行迁移 | Task Packet 明确允许，或实现所必需且影响已说明 | 版本与许可证、迁移影响、可复跑命令 |
| 推送、部署、发布、云资源、外部消息、付费、生产数据写入 | 用户对该具体动作的明确授权 | 目标、环境、影响、回退方式 |

"在本地测试"不等于可读取或修改生产数据；"可以部署"不等于可更换密钥、扩大数据权限或创建付费资源。

## 凭据

只经环境变量或受管密钥机制提供。不写进代码、日志、截图、交接记录或 PROJECT.md。

## 何时继续、何时停下

- 目标、环境、影响都没变 → 在已有授权内连续执行必要步骤，不逐步重复请示。
- 目标换成另一个系统、环境从测试变生产、影响扩大到新数据或新费用 → 先说明变化，取得新的明确授权。
- 需要外部动作时，先做完可本地复查的准备工作（实现、测试、发布说明、回退方案），再请求确认那一个具体动作。

范围或架构变更只是在讨论阶段，也要显式列出未来的授权门：云服务、账号/凭据、付费资源、部署发布、生产数据读写分别由谁在什么条件下确认。分析影响不等于已经获得执行授权。

## 环境与审批是两层

工具的沙箱和审批设置决定"技术上能不能做"；Task Packet 与项目规则决定"属不属于当前任务"。两层都通过才执行；不要因工具未拦截就默认某动作属于任务范围。
