# 变更管理与跨会话

## 单一真相

每类信息只有一个当前来源，其他地方引用而不复制：

| 信息 | 唯一来源 |
|---|---|
| 产品目标与范围 | PROJECT.md 的 Brief |
| 系统边界 | 架构基线 |
| 重要技术取舍 | 关键决定表（重大者写 ADR） |
| 当前工作状态 | PROJECT.md 当前任务 |
| 代码变化 | Git |
| 技术验证 | 测试证据 |
| 运行问题 | 应用日志 |

多个会话各存一套"项目理解"，是状态漂移的主要来源。

## 新需求影响分析

用户中途提出任何新想法（哪怕只是"顺便"），先分析不实现：

1. 判断类型：缺陷 / 优化 / 新功能 / 范围或架构变化。
2. 说明价值，以及对用户流程、数据、接口、权限、费用、部署、已完成工作的影响。
3. 建议归属：现在做 / 本版本稍后 / Post-MVP / 放弃。
4. 若改变已批准架构 → 先形成 ADR 草案，更新基线后再排任务。
5. 变更通过后先更新受影响的真相来源（Brief、里程碑），再实施。

若影响包含云服务、账号/凭据、付费资源、部署发布或生产数据，分析中逐项标明“仅评估”还是“已有具体授权”；未授权时不得把后续外部动作写成默认会执行。

给非技术用户的交接只保留一个可执行下一步：优先由 AI 从现有文件与 Git 中定位入口或缺口；确实缺资料时，明确要用户提供的一个文件、路径或决定，以及提供后会发生什么。

## 跨会话交接

换会话时留下（更新 PROJECT.md 并在对话中给出）：

```text
目标与状态：Task ID / 当前阶段 / 唯一下一步
位置：工作目录、分支或候选版本
工作区：干净 / 有未提交修改（列出属于本任务的文件）
已完成与证据：行为、命令结果、可打开的路径
当前失败或未证实假设：事实 + 下一项检查
待决定事项：没有则写无
```

接手方先读项目状态和交接，核对当前工作区；与记录不一致时，以当前文件、Git、可复跑证据为准。

一次连贯的目标尽量留在同一会话；只有工作真正分支、上下文混杂或需要隔天继续时才交接。

## 状态记录格式

```text
Task: <ID>
Status: TODO / IN PROGRESS / READY FOR REVIEW / ACCEPTED / REJECTED / BLOCKED
Evidence: 验证结果或引用
Remaining: 具体失败项或阻塞（没有则写无）
Next: 唯一下一步
```

## 可复现的开发环境

"我电脑能运行"不等于环境可复现。项目应让干净目录能按明确入口完成：安装依赖、配置本地变量、启动服务、运行验证、停止清理。

- 入仓库：运行时与包管理器版本、锁文件、env.example（变量名、用途、安全默认值）、本地依赖与端口、测试数据来源。
- 不入仓库：密钥、真实用户数据、生产变量值、共享环境凭据。

改动运行时、依赖、配置、迁移或启动方式后，至少在干净环境验证一次：安装成功、服务可启动、核心测试可运行、最短用户路径可用。
