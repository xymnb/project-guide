# 规划：里程碑与任务拆解

适用：Brief 确认后排实施顺序，或已有项目要规划一个功能。母计划给方向和顺序，Task Packet 才是执行单元。

## 先纵向跑通

第一条链路做成端到端最薄闭环：前端 → 服务 → 存储 → 返回界面，刷新后状态仍在。
中间可以用假数据，但网络、持久化、任务流转必须真正连通。
之后逐层替换真实能力，**每次只换一种主要变量**，便于定位问题来自哪一层。
避免前端与后端各自铺完才第一次集成。

## 里程碑计划格式

在 PROJECT.md"里程碑"表中维护，每个里程碑四要素齐全才有效：

| ID | 目标 | 范围 | 准出证据 | 状态 |

- 里程碑证明跨模块链路成立；单个任务通过只证明本任务验收项成立；最终发布还要证明真实使用与部署成立。
- 大任务（涉及多模块、多文件或实现不确定）必须拆成多个 Task Packet，不作为一条开放命令执行。
- 具体文件、接口、迁移、验证方式在任务开始前才展开（Just-in-Time），母计划不预先写死。

## Task Packet（任务施工单）

开始一个实现任务前，先在 PROJECT.md 当前任务处写好：

```text
任务：<ID>
目标：<一个明确可观察的结果>
输入：<相关规格、基线、当前接口>
允许范围：<目录、模块、文件责任>
禁止范围：<本次不能触碰的区域>
依赖与变更权限：<依赖、migration、API 契约是否可改>
操作权限：<可读改范围；可运行命令；是否可装依赖/跑迁移/外部动作>
验收标准：
1. <行为与预期结果>
2. <与此次修改相关的失败或边界情形>
验证：<从当前仓库确认的验证入口，不是猜的命令>
停止条件：<出现什么情况回到决策而非继续改>
```

验收标准在开发前确定；没有它不开工。

## 按任务大小裁剪流程

流程为了减少错误决策，不为每件事写报告。按不确定性、影响范围和可逆性选最短足够路径：

| 情况 | 最小流程 | 何时升级 |
|---|---|---|
| 文案、样式、已定位小缺陷 | 目标 → 最小修改 → 对应检查 → diff 审查 | 发现涉及共享组件、数据或用户流程 |
| 已有项目的明确功能 | 引用基线 → Task Packet → 实现、验证、审查 | 改变核心契约、数据模型或部署方式 |
| 新项目或重大边界变化 | Brief → 产品设计 → 架构 → 里程碑 → Task Packet | 无；这是进入实现前的必要准备 |
| 关键能力不确定 | 有限 Spike | 实验结果改变产品或架构决策 |

## 技术可行性 Spike

触发：产品依赖一项尚未验证的能力（外部服务是否支持所需操作、框架能否满足关键交互、迁移能否安全处理现有数据、协议能否在目标环境连通），且不确定性会改变决策。

有效 Spike 预先写明：

- 要验证的单一问题，以及它影响哪项产品或架构决策。
- 固定的版本、样例输入、最小接口和隔离环境。
- 成功与失败各自可观察的证据，不是"感觉能用"。
- 时间或工作量上限；到顶就输出结论、限制与下一步。
- 通过时采用什么最小方案；失败时走替代还是停止。

Spike 的产物是证据和决策，不是生产代码承诺。实验代码如需保留，说明其后续职责和测试；否则清理。

## 依赖与并行

- 先冻结契约和共享基础（接口 Schema、公共类型、迁移），再让不同任务并行。
- 同一文件、共享迁移、公共类型不并行修改。
- 第一批任务开工前核对五项：目标/范围/输入输出、前置依赖已满足、可判定的验收标准、从仓库确认的验证入口、停止条件。
