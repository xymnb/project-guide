# 设计说明

本文解释 project-guide Skill 的设计取舍、结构与来源，供维护者和评估者理解「为什么是这副样子」。

## 目标与非目标

**目标**：让 AI 在真实开发协作中充当「项目领航员」——主动整理信息、提出下一步、起草产物、实施和验证，同时把目标、关键取舍、真实体验与外部授权留给用户。

**非目标**：

- 不是通用聊天提示词集合，而是一套有阶段、有准出门的交付流程规范；
- 不替代项目管理软件——跨会话状态只用一个 Markdown 文件（`docs/PROJECT.md`）；
- 不追求覆盖所有工程场景，只固化「从一句想法到上线」这一条主线上的纪律。

## 六条原则

1. 先决定做什么，再决定怎么实现。
2. 后续阶段引用上游成果；有新证据才重新决策。
3. 先让一条薄链路跑通，再扩展功能。
4. 一次任务有目标、范围、验收和停止条件。
5. 测试通过、人工验收、真实部署分别证明，不能互相替代。
6. 新需求先分类与评估，不直接变成代码改动。

## 结构：主控 + 按需加载的 references

`SKILL.md` 是常驻主控：阶段地图、准出门、状态文件格式、汇报格式与推进纪律。细则拆成 6 个 references，按情况加载，避免把全量流程塞进每次会话的上下文：

| 文件 | 职责 | 对应阶段 |
|---|---|---|
| kickoff.md | 访谈、Project Brief、MVP、暂定假设 | 立项 |
| planning.md | 里程碑、依赖排序、Task Packet、按任务大小裁剪流程 | 规划（含小改动最短路径） |
| coding-loop.md | READ→…→COMMIT 九步循环、验证选择、排错纪律、Git 纪律 | 实现 |
| acceptance.md | 自动检查、用户可照做的验收引导、发布判定 | 验收/发布 |
| change-control.md | 新需求分类、影响分析、跨会话交接 | 全程 |
| authority.md | 操作权限边界：依赖/迁移/部署/外部动作的授权门 | 全程 |

## 关键机制

- **阶段地图与准出门**：七个阶段各定义「AI 主动完成什么 / 准出证据 / 需要用户确认什么」，规则是不跳门——没有验收标准不开写代码，架构未冻结不做大实现，测试全绿不等于可以发布。
- **统一状态文件 `docs/PROJECT.md`**：跨会话的唯一锚点（Brief、暂定假设、关键决定、里程碑、当前任务、唯一下一步）。每类信息只有一个来源，代码变化交给 Git，不为每轮对话另建进度日志。
- **按任务大小裁剪流程**：小改动走最短足够路径，不启动完整立项与架构流程；这是通过 planning.md 的裁剪规则而非硬编码分支实现。
- **证据分级**：汇报时区分「用户陈述 / 状态文件记录 / 本轮已验证」，未经本轮复验的结果不得写成已确认事实；占位脚本和历史结论不算验证证据。
- **权限两层模型**：工具沙箱决定「技术上能不能做」，任务范围决定「属不属于当前任务」；云服务、凭据、付费、部署、生产数据需要针对具体动作的显式授权，评估不等于授权。
- **范围刹停**：新增一级业务域、换数据库/运行时、改核心契约等信号出现时先停下做影响分析，普通实现困难不自动升级为架构变更。

## 来源与修订模型

本 Skill 最初蒸馏自作者的《Vibe Coding 手册》。该手册及原始调研位于私有 Obsidian 资料库，**不随本仓库发布，也不由发布流程修改**。当前实际运行中的 project-guide Skill 是行为 Source of Truth；本仓库发布与其一致的公开副本，eval/ 是当前正式测试与回归维护位置。研究资料只作为历史与设计来源，需要吸收的新原则应先进入正式 Skill 与评测，再进入公开版本。

手册章节与本 Skill 的主题对应（按章节标题归纳）：

| Skill 部分 | 手册主题来源 |
|---|---|
| SKILL.md 阶段地图 / 状态文件 | 工程起点、架构冻结、立项/验收/发布模板、项目真相与变更管理 |
| kickoff.md | 立项与产品设计、AI 主动带项目 |
| planning.md | 开发规划与任务拆解 |
| coding-loop.md | 工程起点与工作规则、Coding 标准循环 |

## 评测方法概要

评测回答一个问题：装上这个 Skill 的真实 Agent，在典型场景里是否表现出规范要求的行为——而不是措辞是否与手册一致。

- **7 个端到端场景**：从「非技术用户一句想法」到「参考文件被故意移除时的降级行为」，每个场景在临时 Git 工作区（fixture）中通过 `codex exec` 运行真实会话；
- **程序化检查**：预期 reference 是否被实际读取、是否发生未授权写入、耗时与输出规模；
- **三人人设评分**：非技术用户 / 工程负责人 / 验收 QA，各自按 20 分制 rubric 独立打分，18 分以上视为达标；
- **产物**：每次运行落盘 answer/trace/metadata/summary，可复查。

运行方法见 [eval/README.md](../eval/README.md)。
