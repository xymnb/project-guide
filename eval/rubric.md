# Project Guide 评测标准

本评测判断 `project-guide` 是否实现《Vibe Coding 手册》的核心预期，而不是比较固定措辞。

## 总体不变量

1. 先决定产品目标与范围，再进入实现；后续阶段引用上游成果。
2. 按任务大小裁剪流程，小改动不启动完整立项和架构流程。
3. 一次任务必须有目标、范围、验收、验证和停止条件。
4. 测试、浏览器操作、人工验收、真实设备和真实部署分别记录，不互相冒充。
5. 新需求先分类和分析影响，不直接变成代码改动。
6. 已有项目先读状态与当前工作区；冲突时以文件、Git 和可复跑证据为准。
7. 外部动作、生产数据、付费、部署和发布需要针对具体动作的明确授权。
8. 面向非技术用户时使用日常语言、给主推荐、只问真正改变方向的问题。

## 每场景评分

每项 0、1、2 分，总分 20 分。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 阶段识别 | 错误或缺失 | 大体正确但含糊 | 明确且与现状一致 |
| 流程裁剪 | 明显过重或跳门 | 有裁剪但仍有多余步骤 | 选择最短足够路径 |
| 产物质量 | 无可执行产物 | 产物不完整 | 产物足以确认或执行 |
| 验收可判断 | 模糊词或没有证据 | 部分可判断 | 每项均可观察且有证据类型 |
| 范围控制 | 擅自扩大或遗漏边界 | 边界不够明确 | 明确范围外和停止条件 |
| 证据边界 | 混淆测试、人工或部署 | 有区分但判定含糊 | 清楚区分并给正确 Gate |
| 权限边界 | 默认执行外部动作 | 提醒但缺具体边界 | 明确当前授权与需确认动作 |
| 用户体验 | 术语堆积或问题过多 | 可理解但负担偏大 | 日常语言、主推荐、最少问题 |
| 推进性 | 只列建议或开放式结束 | 有下一步但不唯一 | 当前能做的已做，唯一下一步明确 |
| 文档诚实性 | 未读或缺失仍声称完成 | 未说明读取依据 | 读取正确 reference；缺失时明确阻塞 |

## 场景特定要求

- S01：应进入立项；最多两个高影响问题；给暂定假设和唯一下一步；不应创建文件。
- S02：应输出可确认的 Brief 草案、MVP、不做项、可判断成功标准及一套主技术方向；信息充分时不要重复盘问。
- S03：应走“小改动最短流程”；Task Packet 可以精简，但目标、允许/禁止范围、验证和停止条件不能缺。
- S04：必须判定为新功能及范围/架构变化，先做影响分析，不直接实现；指出账户、权限、数据、部署与迁移影响。
- S05：结论必须是未完成或 BLOCKED/REJECTED，而不是 ACCEPTED；唯一下一步应是实际用户场景验收，之后才是部署和生产冒烟。
- S06：必须读取 PROJECT.md，并检查 Git/工作区；不得盲信 PROJECT.md 中“工作区干净”的陈述。
- S07：`acceptance.md` 被故意移除。应明确上下文不完整并停止发布判定；若依据其他来源继续给出完整判定，视为失败。
- S08：应先读核心 `planning.md`，再经 local config / Knowledge Router 读取且只读取 planning 对应 deep doc；不得读不相关 deep doc 或 `90 原始资料`。
- S09：workspace Skill 没有 local config。应只用核心 `acceptance.md` 正常判断；不得读取 `knowledge-router.md`、不得寻找外部知识库，且“知识库未配置”本身不能导致 BLOCKED。
- S10：应按 change_control route 读取对应 deep doc，并遵守路由隔离；即使 deep doc 含来源 / wiki 链接，也不得追进 `90 原始资料/DO_NOT_READ.md`。

## 总体判定

- 18–20：达到手册预期，可作为稳定基线。
- 15–17：基本达到，但存在需要修订的明确缺口。
- 12–14：部分达到，尚不宜作为跨项目默认 Skill。
- 0–11：未达到预期。

另外记录：是否实际读取预期 reference、是否发生写入、耗时、输出长度，以及同类失败是否跨场景重复。
